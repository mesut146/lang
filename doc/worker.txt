worker teardown redesign (done 2026-10-07, was future work)

status: 20_worker green with drops on (own section, repeated runs) and
off. the redesign below is implemented in src/std/th.x; this note now
records what was wrong and why the fix looks the way it does.

problem
-------
tests/std_test/20_worker.x panics under drops with
  Mutex<LinkedList<Box<WorkerBridgeInfo>>>::drop(*self)
  mutex destroy failed, code=16
code 16 is EBUSY: pthread_mutex_destroy on a locked mutex.

evidence (all reproduced, not theorized)
- drops-off: green (nothing is ever destroyed, so nothing is checked).
- drops-on: Any::drop panic first (fixed by making Any::drop total,
  commit b599365); then EBUSY deterministically enough to fail the suite.
- the panic fires in worker teardown after join() returned, never in
  worker_bridge itself.

root cause
----------
threads remove THEMSELVES from worker.infos when done, then exit freely.
Worker::join waits only for the queue to drain (infos.empty()), never
pthread_joins anyone (a join attempt via the infos list is commented out
at th.x:224 - the handles vanish together with the removed nodes).
so join() can return, the test can end, and Worker can drop while a
worker thread is still inside worker_bridge holding infos or todo.
destroying a held mutex is EBUSY, correctly reported.

additionally the test is racy even drops-off: threads may touch freed
worker memory after join; it just never crashes observably there.

what not to do
--------------
- retry-on-EBUSY or tolerant destroy in Mutex::drop: masks the race,
  keeps the use-after-free. EBUSY here is a true report.
- joining via the infos list (th.x:224 shape): nodes self-remove, so the
  handle you want is already gone by the time you look for it.

redesign direction (implemented)
------------------
retain join handles outside the self-removing list (Worker.threads, no
mutex needed: only the owning thread touches it), and join-before-destroy
with quiescence: drain, join all recorded, re-check, repeat (todo refill
can spawn mid-join; spawns are finite so it terminates). worker_bridge
removes SELF, never peers: freeing another live thread's node was the
use-after-free behind garbage sleeps (~261-year msleep observed) and the
EBUSY that followed. after self-removal nothing touches `info` again
(worker ptr was copied beforehand); the old len==1/clear() special case
is subsumed by uniform self-search.

separately fixed while here: Mutex::drop unconditionally unlocked before
destroy, corrupting the counter to -1 on every already-unlocked mutex, so
destroy could never succeed (even single-threaded, zero jobs). drop now
destroys directly; a held mutex at destroy stays loud (EBUSY) as it
should. an unconditional unlock would also have been wrong.

related, done
------------
- Any::drop no longer panics (frees shell + type string; payload innards
  leak without per-T glue). drop2 is complete (innards + shell + type).
- LinkedList::remove drops bypassed vals; with Any payloads that is now
  safe (no panic), leaking only heap-owning innards.

follow-up: two more bugs in the same path (2026-10-19)
------------------------------------------------------
The redesign above assumed `Worker.threads` needs no mutex because only the
owner touches it -- but worker_bridge, after finishing a job, pulled the next
queued job itself and called Worker::add_arg, which appends to `threads`. So a
finishing worker did touch it, concurrently with join()'s remove(0):

- heap corruption: 40 modules through `-j 4` abort deterministically (10/10)
  after a dozen jobs with "corrupted size vs. prev_size"
  (malloc_consolidate(): invalid chunk size under MALLOC_CHECK_=3) -- two
  concurrent List::add reallocs (plus a remove(0)) on the same buffer.
- the lost-node variant shows up as a hang: a worker's completion node could be
  dropped, so join() polled `infos` forever with nothing left to run (a
  ~45-minute hang of the full suite during the v1.18 dry run, and a rare hang
  of the inc gate).

Fix: workers never start jobs. worker_bridge runs its job, retires SELF and
returns. join() (the owner) hands queued jobs to fresh workers while slots are
free, waits for `infos` to empty, joins the retained handles, and stops only
when both `infos` and `todo` are empty -- a job stays queued whenever every
worker was busy when it was enqueued, and nothing else picks it up now. The
"only the owner touches threads" invariant is true again and is stated in the
struct comment. (An earlier attempt to write this broke liveness exactly there:
the exit test checked `infos` only, so queued jobs were never started and the
link failed with undefined references.)

The second bug is unrelated to the pool's design. CompileArgs carried
`idx: Mutex<i32>*`, initialized with the address of a *loop-local* `let idx =
Mutex::new(0)` in compiler.x's enqueue loop. Jobs run later, in a worker
thread, so `args.idx.lock()` took a pthread mutex living in a dead stack frame
whose bytes the next call reused: locking that garbage either succeeded by luck
or waited forever -- a worker blocked with no output, which is the flaky hang.
The field was dead anyway (incremented, never read) and was removed together
with the two lock/unlock pairs in the verbose prints.

Regression: bin/test.sh's inc gate now compiles 40 generated modules through
`-j 4` with MALLOC_CHECK_=3, so the allocator makes the corruption loud instead
of it aborting later. Pre-fix the gate fails 3/3 (abort); post-fix 20/20
standalone stress runs and 8/8 inc gates are clean.
